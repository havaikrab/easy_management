# Easy Management

[![CI](https://github.com/havaikrab/easy_management/actions/workflows/ci.yml/badge.svg)](https://github.com/havaikrab/easy_management/actions/workflows/ci.yml)

REST API системы контроля исполнения задач внутри организации: иерархия задач и подзадач, права по должностям, автоматическое назначение исполнителей.

*English: backend for task tracking inside a company. Django REST Framework, JWT, PostgreSQL, Celery + Redis, Docker, CI/CD with GitHub Actions.*

## Возможности

- Дерево задач: у задачи может быть родитель, срок подзадачи не может превышать срок родительской задачи.
- Исполнитель назначается вручную или автоматически. Автоматически выбирается свободный сотрудник нужной должности с наименьшим числом активных задач. Если подходящих нет, задача получает статус «Выполнение прервано».
- Должности и связи между ними (`partners`): исполнителем может быть сотрудник должности, связанной с должностью заказчика.
- Статусы задачи: создана, обрабатывается, выполнение прервано, просрочена, отменена, успешно завершена.
- Celery Beat периодически переводит задачи с истекшим сроком в статус «Просрочена» (интервал задаётся переменной `CELERY_EXPIRED_STATUS_CHECK_INTERVAL`, по умолчанию 30 минут).
- Эндпоинт со списком «застрявших» задач (без исполнителя или прерванных) и кандидатами на их выполнение.
- Эндпоинт с деревом подзадач и их состоянием.
- Регистрация сотрудников ограничена: её выполняют только пользователи с соответствующим правом (например, отдел кадров).
- JWT-аутентификация, фильтрация, поиск, сортировка, пагинация.
- Документация API в Swagger UI и ReDoc (drf-spectacular).

## Стек

Python 3.13, Django 6, Django REST Framework, SimpleJWT, django-filter, drf-spectacular, PostgreSQL 16, Redis, Celery и Celery Beat, Gunicorn, nginx, Docker Compose, GitHub Actions, Poetry, flake8.

## Быстрый старт (разработка)

1. Клонируйте репозиторий и создайте `.env` по шаблону `.env_template`:
   ```bash
   git clone git@github.com:havaikrab/easy_management.git
   cd easy_management
   cp .env_template .env
   ```
2. Заполните в `.env` как минимум `SECRET_KEY`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` и данные первого суперпользователя (см. ниже).
3. Запустите контейнеры:
   ```bash
   docker compose up -d
   ```
4. Откройте документацию API: <http://localhost:8000/api/schema/swagger-ui/> (ReDoc: `/api/schema/redoc/`, админ-панель: `/admin/`).

В режиме разработки сервис запускается на встроенном сервере Django. Compose поднимает PostgreSQL, Redis, Celery worker, Celery beat и веб-приложение.

### Первый суперпользователь

Регистрировать сотрудников может только ограниченный круг лиц, поэтому при первом запуске нужен суперпользователь. Задайте в `.env`:

```env
CREATE_SUPER_ADMIN=True
SUPER_ADMIN_ACTIVITY=Директор
SUPER_ADMIN_NAME=admin          # до 12 символов, нужен для входа в админ-панель
SUPER_LAST_NAME=Иванов
SUPER_FIRST_NAME=Иван
SUPER_PASSWORD=<ваш пароль>
```

Команда безопасна для повторных запусков: если пользователь с `SUPER_ADMIN_NAME` уже существует, создание пропускается и в лог пишется информационное сообщение, поэтому перезапуск сервера с `CREATE_SUPER_ADMIN=True` не вызывает ошибок. После первого запуска флаг всё же лучше выключить (`CREATE_SUPER_ADMIN=False`) или удалить переменную. Ошибка возникает только если пользователя ещё нет, а обязательные значения (`SUPER_ADMIN_ACTIVITY`, `SUPER_ADMIN_NAME`, `SUPER_LAST_NAME`, `SUPER_FIRST_NAME`, `SUPER_PASSWORD`) не заданы или пусты.

Дальше суперпользователь:
1. входит в админ-панель;
2. описывает должности организации;
3. создаёт учётные записи ключевых сотрудников и назначает им права.

## Права доступа

| Право | Что даёт |
|---|---|
| `add_activity` | создавать и изменять должности и связи между ними |
| `view_activity` | регистрировать сотрудников, просматривать должности |
| `view_quest` | просматривать дерево зависимостей задач |

Суперпользователь обладает всеми правами. Обычный сотрудник видит задачи, где он создатель или исполнитель.

## Основные эндпоинты

| Метод и путь | Назначение |
|---|---|
| `POST /users/login/`, `POST /users/token_refresh/` | получение и обновление JWT |
| `/users/` | сотрудники (регистрация, просмотр, обновление) |
| `POST /users/change_password/` | смена пароля |
| `GET /users/candidates/<activity_id>/` | доступные сотрудники должности, отсортированные по загрузке |
| `/activities/` | должности |
| `/activities/<id>/partners/<partner_id>/` | управление связями между должностями |
| `/quests/` | задачи (фильтры, поиск, сортировка, пагинация) |
| `GET /quests/<id>/tree/` | дерево подзадач |
| `GET /quests/important/` | задачи без исполнителя или с прерванным выполнением и кандидаты на них |

Полное описание параметров и примеров запросов находится в Swagger UI.

## CI/CD

GitHub Actions (`.github/workflows/ci.yml`) состоит из четырёх job'ов:

1. `lint`: flake8 и black (`--check`).
2. `test`: тесты на PostgreSQL 16 (`manage.py test` сам создаёт тестовую БД и применяет миграции).
3. `build`: сборка Docker-образа. Публикация в Docker Hub (тег по хэшу коммита) выполняется только при push в `main`.
4. `deploy`: подключение к серверу по SSH и обновление `docker compose` с новым образом.

Что запускается в разных ситуациях:

| Событие | lint + test | build | Публикация образа | deploy |
|---|---|---|---|---|
| Push в любую ветку | да | нет | нет | нет |
| Pull request в `main` (открытие, новые коммиты) | да | да (проверка Dockerfile) | нет | нет |
| Merge PR в `main` (это push в `main`) | да | да | да | только если включён |

Пока PR открыт, каждый новый коммит запускает проверки дважды: по событию `push` (проверяется ветка) и по событию `pull_request` (проверяется результат слияния с актуальным `main`). Устаревшие запуски в ветках и PR отменяются автоматически, запуски в `main` не отменяются, чтобы не прервать деплой.

### Настройка репозитория

Secrets (Settings → Secrets and variables → Actions → Secrets):

| Секрет | Назначение |
|---|---|
| `DOCKER_HUB_USERNAME`, `DOCKER_HUB_ACCESS_TOKEN` | публикация образа; без них `build` только собирает образ |
| `SERVER_IP`, `SSH_USER`, `SSH_KEY` | адрес сервера, пользователь и приватный ключ для подключения по SSH |
| `SSH_KNOWN_HOSTS` | отпечаток ключа сервера, получить командой `ssh-keyscan -H <SERVER_IP>` |

Variables (Settings → Secrets and variables → Actions → Variables):

| Переменная | Назначение |
|---|---|
| `DEPLOY_ENABLED` | `true` включает job `deploy`. Пока переменная не задана (нет сервера), деплой пропускается |

Для merge в `main` рекомендуется включить branch protection rule с обязательным pull request и обязательными проверками `lint`, `test` и `build`.

## Развёртывание на сервере

1. Скопируйте содержимое папки [`deploy/`](deploy/) в рабочую директорию на сервере.
2. Создайте рядом файл `.env` (шаблон: `.env_template`) и укажите `IMAGE_NAME` с именем образа.
3. Выполните `docker compose up -d`.

При автоматическом деплое через CI файлы из `deploy/` копируются на сервер в директорию `~/easy-management/`, а в `.env` обновляется только `IMAGE_NAME`. Остальные значения в `.env` (ключи, пароли БД, CORS) нужно создать на сервере вручную до первого деплоя. Также на сервере должен быть установлен Docker.

В продакшен-конфигурации приложение работает под Gunicorn за nginx. Для доступа с внешнего адреса укажите `CORS_ALLOWED_ORIGINS` и `CSRF_TRUSTED_ORIGINS`.
